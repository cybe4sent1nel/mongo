Bidirectional-field sync bypasses SCF's access control on the save path most sites actually use

Secure Custom Fields' 6.9.5 changelog documents a fix for unauthorized bidirectional-field writes — scoped, by its own wording, to REST updates. The classic post-edit screen and the standard Gutenberg block-editor save use a different path entirely, and it has no such check.

Description

One shared write function, two checks bolted on beside it

SCF's Relationship, Post Object, User, and Taxonomy fields support a Bidirectional setting: when field A on object X is marked bidirectional with a target field B, saving A on X doesn't just store the selected IDs on X — it also reaches out and updates B on every object A's value points at, adding or removing a back-reference to X. The write to that target object happens with no check that the acting user is allowed to edit the target — only that they can edit X, the object actually being saved.

SCF's own 6.9.5 changelog (Release date 7 August 2026 — the version this was found in) documents a fix for exactly this bug class:

“REST updates now reject bidirectional field writes when the current user cannot edit an inverse target.”

That sentence names its own boundary: REST updates. The fix is real, and I verified it holds. What it doesn't cover — and what remains fully exploitable, with no special configuration — is the save path every classic post-edit screen and every standard Gutenberg block-editor save actually uses. An Author (the lowest role that can be granted this field) can use a completely ordinary save of their own post to force a write into a post owned by someone else, that they otherwise cannot edit at all.

	...

$target_item_ids is the field's submitted value — the post IDs the saving user selected. enable_bidirection is true by default (secure‑custom‑fields.php:171 ↗). Relationship/Post Object fields never filter selectable results by whether the selecting user can edit the candidate — only by the field's own type/status/taxonomy config — so any post the field is configured to allow can be used as $addition.

4The unprotected path is what every default install uses

form-post.php:44 ↗ hooks the classic save handler onto WordPress core's own save_post action, which calls acf_save_post() (form-post.php:340–375 ↗) → _acf_do_save_post() → acf_update_values() → acf_update_value() → the field's update_value() (acf-form-functions.php ↗, acf-value-functions.php ↗) — none of which call acf_current_user_can_edit_in_context() or anything equivalent.

This save_post hook fires for both the classic post-edit screen (a plain form POST to wp-admin/post.php) and the standard Gutenberg block editor's save of non-block meta box data — which WordPress core implements as an AJAX request to wp-admin/post.php?meta-box-loader=1 that itself triggers save_post the same way. form-gutenberg.php:173–179 ↗ confirms SCF is explicitly aware meta-box-loader requests reach this path — its one Gutenberg-specific hook checks for that flag to relax validation, not to swap the save mechanism. No REST client, no special settings, no Classic Editor requirement.

Impact

Attacker privilege, impact, and CVSS

author1, role Author — the lowest role SCF's UI lets you attach a Relationship field to by default. Confirmed via Proof D that this account has zero standing access to the victim post. User interaction: none. The entire chain is a single ordinary save of the attacker's own content.

Any user who can edit an object carrying a bidirectional-enabled field (on by default) can force a write into any other object the field is configured to allow selecting — not filtered by whether the selecting user can edit the candidate, only by type/status/taxonomy. Concretely: unwanted relationship references injected into content owned by other users or managed by higher-privileged roles, and — because the same code path handles removals — existing references silently stripped from objects the attacker cannot edit. Written values are object IDs, not arbitrary strings, so this is not a stored-XSS primitive; it is a directly-demonstrated broken access control / IDOR-class vulnerability.

Honest limits

What this isn't

  • Not a content-injection/XSS primitive — written values are object IDs.
  • Requires a bidirectional field configured and reachable by the attacker's role — an admin decision, though the feature is on by default and designed for exactly this use.
  • Front-end acf_form() and the Classic Editor plugin weren't separately re-verified — both use the same save_post mechanism per the code trace, but that's reasoned, not independently tested.
Exclusions considered

Against the program's own list

  • “Admins/editors can post JS” — no JS or unfiltered_html involved anywhere.
  • CVSS < 4.0 — 4.3 clears it, shown with reasoning above.
  • Out-of-scope plugin — SCF is explicitly named under “Official WordPress plugins.”
  • Not scanner output — every claim manually built, executed, and quoted verbatim.
Recommendation

Fix the write path, not each entrypoint

Move the capability check into acf_update_bidirectional_values() itself (or _scf_prepare_bidirectional_update(), which already computes the exact destination list) rather than only pre-flighting it at the REST dispatch layer. That closes the gap for every save entrypoint — classic form, Gutenberg meta-box-loader, REST, front-end acf_form(), and any programmatic update_field() call — at once, instead of requiring a separately-added pre-flight hook per entrypoint, which is how this gap happened: two REST-specific pre-flights exist (one gated behind a default-off flag), and the entrypoint the vast majority of saves actually use has neither.

Prior art

Duplicate check

No public CVE or advisory found for this specific issue — wp-safety.org currently lists Secure Custom Fields as having no known CVEs; a search for “Secure Custom Fields bidirectional access control CVE” returned only an unrelated, long-fixed admin-only stored XSS in field labels (≤6.3.8 / ≤6.3.6.2) — different sink, different fix, different versions, predating the bidirectional feature's REST fix by multiple releases. HackerOne's own Hacktivity for this program couldn't be checked directly (network egress to hackerone.com is blocked in my environment), so an undisclosed duplicate can't be ruled out with full certainty.
