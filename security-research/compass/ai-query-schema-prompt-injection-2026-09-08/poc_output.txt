Caveat: this run used JSON.stringify as a stand-in for the real toJSString()
(from mongodb-query-parser, not installed in this sandbox), which happens to
render the payload's newlines as the two-character escape "\n" rather than a
raw line break, and wraps the key in escaped quotes. The vulnerability itself
-- flattenSchemaToObject() passing the field name through with no sanitization,
and gen-ai-prompt.ts never calling anything like escapeUserInput() on the
resulting schema string -- is unaffected by which stringifier is used. What is
NOT verified here, for lack of API access to MongoDB's actual Atlas AI backend,
is how strongly a real deployed LLM is swayed by instruction-like text arriving
inside a JSON-quoted object key versus arriving as a clean unescaped line break
-- prompt injection via untrusted data is a well-documented general class
(OWASP LLM Top 10, LLM01), but its real-world success rate is model- and
guardrail-dependent and I have not measured it against the live service.
