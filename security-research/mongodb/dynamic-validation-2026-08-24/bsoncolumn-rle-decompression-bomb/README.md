## Severity: Critical — CWE-400 (Uncontrolled Resource Consumption)

A user with ordinary write access to a timeseries collection's backing `system.buckets.<coll>`
namespace (reachable with plain `readWrite` privilege — direct writes to `system.buckets.*` are
logged but not blocked) can craft a single bucket document whose compressed `data.*` columns
decode, via MongoDB's own Simple8b run-length-encoding, to hundreds of millions of logical
elements from a write of only a few megabytes. An ordinary aggregation query against the logical
timeseries collection (not any internal-only command) then decompresses that column during normal
`$_internalUnpackBucket` processing, and — with no size/memory limit currently enforced on that
decompression — drives `mongod`'s RSS up linearly with decode progress until the kernel cgroup
OOM-killer terminates the process outright.

## Root cause

`SERVER-117617` had added a real defense: `bsonMaxExpandedMemUsage` (default 200MB,
`bson_validate.idl:64-68`, `d100bf19961251f273e1d0bd8ce66fc60634f53c`) plus a
`DecompressedMemoryEstimator` class that walked a `BSONColumn` during validation, correctly
accounting for RLE amplification, and rejected documents whose *decompressed* size would exceed
the limit. **This exact revert commit removes that defense entirely** — the commit's own subject
line is `SERVER-130991 Revert "SERVER-117617 Add runtime memory limits on uncompressed size for
BSONColumn in BSON validate" (#58926)`, and it's what `r8.3.8` actually ships:
`https://github.com/mongodb/mongo/commit/d100bf19961251f273e1d0bd8ce66fc60634f53c`. The
`bsonMaxExpandedMemUsage` server parameter still exists and is still settable
(`bson_validate.idl:64-68`) — it is now **dead code**, read by nothing, creating a false sense of
protection for any operator who sets it expecting it to still do something.

## Why write-time structural validation does *not* catch this

`bson_validate.cpp`'s BSONColumn content check (`bson_validate.cpp:541`,
`if (subtype == BinDataType::Column && _validationVersion >= V2_Column) { ... }`) still runs on
every write and does catch a class of *structural* forgeries — confirmed separately in this
program's static/dynamic sweeps that it correctly bounds-checks an interleaved-mode reference
object's declared size against the real buffer end before trusting it (`ColumnValidator` /
`doValidateBSONColumn`), closing off a naive buffer-overrun variant of this attack. Timeseries
bucket writes are also checked by `_validateCompressedMinMax()`
(`src/mongo/db/timeseries/timeseries_bucket_validation.cpp:159-191`), which calls
`bsoncolumn::count(binary, len)` (line 184) and `uassert`s the result equals the bucket's declared
`control.count` — this genuinely blocks the naive attack of inflating one field's declared count
without updating the others to match.

**None of these checks account for RLE amplification's *decompressed* size** — they check
structural well-formedness and count-consistency, not how large the column becomes once decoded.
A **self-consistent** oversized column — where every `data.*` field and `control.count`/`min`/`max`
mutually agree, and the interleaved-mode structural bounds (where applicable) are respected — sails
through every currently-active check and is only expensive once something actually iterates it.

## Mechanism: Simple8b RLE amplification

MongoDB's BSONColumn format (`BinData` subtype 7) is Simple8b-encoded: a literal control byte (the
BSON type of the base element) + empty field name + raw value bytes, followed by Simple8b-encoded
control/data words, terminated by `0x00` (EOO). Simple8b's run-length-encoding selector
(`simple8b_helpers.h:88-90`, verified unchanged at `r8.3.8`):
```cpp
static constexpr uint8_t kRleSelector = 15;
static constexpr uint8_t kMaxRleCount = 16;
static constexpr uint8_t kRleMultiplier = 120;
```
An RLE word (selector `15` in the low 4 bits, count-1 in bits 4-7, max count 16) repeats the
previous value `120` times per count unit — up to `120 × 16 = 1,920` logical repeats from a single
8-byte word. A control byte (`0x80 | (numBlocks-1)`) governs up to 16 such words, so one 129-byte
"section" (1 control byte + 128 data bytes: 16 × 8-byte words) decodes to up to `16 × 1,920 =
30,720` logical elements. Chaining `N` such sections multiplies linearly: `N × 30,720` elements
from `N × 129` bytes of column payload — an amplification ratio in excess of 200:1 in raw bytes
alone, before accounting for each logical element's own materialized BSON representation once
decoded (`BSONColumn::size()`, `bsoncolumn.cpp:755`, confirmed to walk the full decoded sequence
via the iterator rather than compute a cheap closed-form count — decoding genuinely materializes
every element through the allocator).

evidence files, which did not survive the container reset — regenerate via `exploit.py`/
`trigger_query.py` at increasing `N_SECTIONS` once a binary is available. The crash row's figures
are preserved verbatim from this program's own record at the time.)

At the crash scale, the write itself (an ordinary `update` against `system.buckets.<coll>`,
matched=1/modified=1 — accepted cleanly, no validation error) was independently slow enough to
register as a slow-query log entry in its own right (~8.1 seconds of wall time / CPU just running
structural and count validation over the crafted columns) — a secondary, cheaper-to-trigger
CPU-exhaustion data point ahead of the read-side amplification. The triggering read was an ordinary
`$_internalUnpackBucket`-backed query against the *logical* timeseries collection (reached via
normal view resolution — `$_internalUnpackBucket` is what runs on every query against a timeseries
collection, it is not a special/internal-only entry point a client has to invoke directly), such
as `{"$_internalUnpackBucket": {...}}` producing a real aggregation that needs the actual field
value, e.g. `$sum` on the compressed measurement field (a `{"$count": "n"}`-only query would answer
from `control.count` bucket metadata without ever decoding the column — this distinction determines
which queries actually trigger the vulnerability).

`mongod`'s RSS grew essentially linearly with elapsed decode time, with no throttling, backpressure,
or early-abort of any kind, until the kernel cgroup OOM-killer terminated the process outright —
confirmed independently both by the kernel's own `dmesg` oom-kill log line (naming `mongod`'s pid,
the cgroup memory limit, and anon-rss at time of kill) and by `mongod`'s own instrumentation on next
startup reporting an unclean shutdown (`"Startup from clean shutdown?": false`) and an unclean
FTDC shutdown (interim file found, some metrics lost). No graceful degradation of any kind: the
triggering client got no response (connection torn down at the kernel level when the process died),
`mongod`'s log ends abruptly mid-checkpoint with no shutdown message, and every other connected
client is dropped simultaneously. The malicious bucket document persists on disk, so the very next
ordinary read after an operator restarts the process crashes it again.

## Why this is different from the two rejected findings in this program

- Not the `$_internalUnpackBucket` missing-authz finding (closed Informative — reading a bucket via
  that stage doesn't cross a privilege boundary the caller doesn't already have via `find` on the
  same collection). This finding needs only an ordinary, ***ordinary-privilege*** write to
  `system.buckets.*` (already-established as reachable with plain `readWrite`) followed by an
  ordinary read — no internal-only stage invocation required at all, and the impact (process-wide
  crash) is a different security property (availability, not access control) from what that
  rejection addressed.
- Not the `$_internalApplyOplogUpdate` OOM finding (a completely different stage, different code
  path, different amplification mechanism — see `../internal-apply-oplog-update-oom-crash/`).

## Suggested fix

Restore (or re-implement) `SERVER-117617`'s runtime decompressed-size accounting — a
`DecompressedMemoryEstimator`-shaped walk over the BSONColumn during validation, correctly
accounting for RLE amplification (`count × kRleMultiplier` per selector-15 word, summed across all
chained sections), rejecting documents whose *decompressed* size would exceed
`bsonMaxExpandedMemUsage`. Independently, `$_internalUnpackBucket`'s decode path could itself
enforce a memory budget during decompression, rather than relying solely on write-time validation
to have caught everything — a defense-in-depth measure against any future write path that manages
to bypass validation (replication apply, restore from an untrusted backup, storage-engine-level
corruption) reaching the same amplification.
